# L3 ownership — one-page decision brief

**The ask:** decide whether the schema-growth loop (L3 / GRAPHLEARNS) is **a distinct program** or
**`NFRA_TOOLARCH`'s chartered work continued upward**. The spec names this as yours + CTO~Z's, and it is
now the *only* thing blocking L3. Nothing is opened until you rule — no program code, per the spec's own
instruction.

**Why now:** the question was previously hypothetical. **As of today it is concrete — L2's output
exists.** COMPLEARNS L0–L2 is built and verified: the vocabulary is ratified at v1.0 with emission live,
four L1a sensors and the L1b reference sensor emit conformant reports, and the L2 aggregate collects,
ranks, and declares its own denominators over them. The thing whose ownership is in question is no
longer a design; it is a running artifact with a shape you can look at.

**A note on the question itself:** it was recorded in three docs as `GRAPHLEARNS`-vs-`NFRA_ARCHTOOL` — a
program that has since been **renamed to `NFRA_TOOLARCH` and chartered P0**. Anyone answering it was
answering about the wrong entity; corrected today.

## What L2 actually produces (the thing being owned)

- Per-`(cell × address_space)` counts across the sensor fleet, never summed across incommensurable spaces.
- **Applicability denominators**: "M of N tools have a doc plane," with N/A never rendered as 0.
- **Method-mix bias, per cell** — which measurements under-report and by what method.
- **Raw accounting lines with reconciliations** — each sensor shows its own arithmetic, so downstream
  derivations *can disagree with it*. This is what makes L2 itself verifiable.
- **Coverage of itself**: named emitters, named **non**-emitters, and an honest `UNKNOWN` for the
  fleet-wide eligible population — which is, per the spec, **GRAPHLEARNS's hard ceiling**.

## The decision, stated as the real fork

`NFRA_TOOLARCH` (MECHANICAL layer, chartered P0) owns *"archetype census → pattern inventory → stability
grader → tool synthesis/registration/testing; **materializes denominator coverage spaces**."* That last
clause is adjacent to — arguably inclusive of — what L2 feeds. Hence the genuine ambiguity.

L3's distinguishing feature is **the inference gate**: the step where something decides the ontology
needs a *new axis*. The founding literature is explicit that this is not mechanical — *"determinism
computes the residue, it cannot interpret it,"* and inference is rationed to naming a new dimension and
must pay for itself in new determinism (a traversal, a moving predicate, a version pin, and a mutant
proving the predicate can redden).

## Recommendation: **distinct program** — with TOOLARCH as its consumer, not its owner

They differ **in kind, not in scope**. TOOLARCH is chartered as the *mechanical* layer; L3 is a
*semantic-commitment* loop. Folding L3 into TOOLARCH puts an inference gate inside a program defined as
mechanical — which is precisely the grain error the ontology docs warn about (*A is mechanical; B and C
are both SEMANTIC*). The clean split: **L2's output flows to TOOLARCH as input** (it materializes
coverage spaces from it, mechanically), **and separately to L3, which is the only thing permitted to
propose a new axis.** One consumes; one legislates.

**What the decision retires either way:** nothing yet — no L3 code exists, deliberately.

**Options:** (a) distinct program *(recommended)*; (b) TOOLARCH's work continued upward — fold L3 in and
retire the GRAPHLEARNS name; (c) defer — L3 stays blocked, COMPLEARNS keeps producing reports nobody
consumes upward. Any of (a)/(b) unblocks; (c) is stable and costs only the growth loop.
