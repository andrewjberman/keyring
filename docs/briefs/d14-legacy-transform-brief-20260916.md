# PART I -- THE OUTCOME TERRITORY

Each is one thing a named kind of person can DO that they cannot do today. Qualitative; no number invented here.
The person in every outcome is the one who has to act on a legacy product: the COO lane cutting a migration, the CTO
writing its PRD, the worker executing a wave, and Andrew ruling on what the run surfaces.

### O1 -- A seat names a subject and gets back ONE contract naming every resource that composes it, each row carrying the instrument that found it

A seat types the subject -- a product (`mdpf`), a firm pipeline (`49financial` on `blackdiamond`), a bucket
(`opal-data-inf`) -- and receives one structured file in which every trigger (EventBridge RULE and Scheduler SCHEDULE,
both), every script, every Lambda, every EC2 runner and ECS task, every IAM role, policy and instance profile, every
secret, every bucket and every tier plane inside it, every queue, topic, alarm and log group, every Terraform file
that declares any of them, and every served route that reads any of them, is one row. Each row states the instrument
that produced it, its locator, its vintage and the denominator of the class it was drawn from. Today that inventory is
assembled by hand per project: the D8 legacy-firm-buckets brief spent seven findings (IV.1-IV.4, IV.7-IV.9) and 452
lines building it for three buckets, and the MDPF brief did it again for one product. **A resource the run could not
see is a row whose status says so, never a missing row** (ATOM_DECOMP Rule 6: tool failure is a coverage limitation).

### O2 -- A reader sees every fork named as a fork, with the one canonical member marked

Where two things do one job -- a JSON twin beside a parquet gold (`schwab/08335338/gold/` 2,108 / 2,108), a
`bronze_legacy/` beside `bronze/`, two gold trees for one product (`gold/mdpf_revamp/` and `portal/gold/`), a
`bd-`-named runner beside a `49f-`-named one, two Terraform declarations of one function -- the contract carries a
FORK row that names the members, the one job they share, and which member is canonical under the canon. Today a fork
is discovered when a seat trips over it; the memory record of the `bd -> cot` fork-shadow class and R18's own census
row are both after-the-fact finds. **A fork is detected by the DESIRED twin, not by pattern-matching names:** two
current resources whose computed canonical form is the same string are one job done twice (IV.5).

### O3 -- A reader reads any resource's DESIRED name and address beside its CURRENT one, and the desired one was computed, never typed

Every row carries two halves: CURRENT (what is deployed, measured) and DESIRED (what the canon says it should be). The
DESIRED half of a key is `address()`'s output; of a resource name, `name()`'s; of a bucket, the bucket grammar's; of a
verdict, `grade()`'s. **No seat authors a desired string.** Where the builder RAISES or refuses, the row's desired half
reads the refusal verbatim and names the registry row that is missing (Rule 30) -- and that missing row is itself a
finding the run returns. Today the D8 briefs' IV.5 sections are canonical path strings written BY HAND and marked
"PROPOSAL, for L4 to ratify"; the builders that would have produced them landed after those briefs
(`lib/opal_naming.py` `key()`/`address()`/`name()`, cell EN-b-1).

### O4 -- A migration engineer reads the tensions between the two halves as a typed, ranked set, and can dispute the rank because its rule is printed

A tension is one row's CURRENT half disagreeing with its DESIRED half, typed by the axis it departs on (A1 ingestion,
A2 bucket structure, A3 naming, A4 compute, A5 format, plus process and identity -- the canon's own axes, sect. 2) and
by the rule it collides with (R-ids). The set is ordered by the ranking rule the tension map already uses and Andrew
already accepted: LIVE x CLIENT-FACING x RULES-COLLIDING x IRREVERSIBLE, with object count as a tiebreak
(`08_TENSION_MAP.md` sect. 0). Each factor is a MEASURED value on the row (live: newest write against the trading-day
frontier; client-facing: a served route reads it; colliding: the count of R-ids; irreversible: the canon's own word,
as parquet-under-bronze is under R9). **The rule is printed at the top of the set so a reader can contest the order,
and no weighting is invented here** (Part III).

### O5 -- A reader reads a flow diagram of the subject and it agrees with the contract by construction

The diagram -- triggers on the left firing compute in the middle writing tiers on the right, with the serving routes
that read them, in the house `/draw` style -- is GENERATED from the contract's rows and edges, never drawn beside it.
Two diagrams exist per run, current and desired, from the two halves. A diagram is a VIEW over the ledger (ATOM_DECOMP
"Run the frontier": *"Diagrams are views over ledgers, not sources of truth"*); a reader who finds the diagram and the
contract disagreeing has found a defect in the renderer, never a second truth.

### O6 -- A COO lane cuts an R19 migration's decomposition FROM the remediation plan, not from archaeology

The plan is the ordered set of atomic work packages that close the tensions: each with one objective, its reads, its
writes, its acceptance proof, its rollback, its owner and its replacement obligation (ATOM_DECOMP "Decompose
migration"), in the six-step order the canon rules (R19). A COO lane at L5 reads the plan as the decomposition's
substrate, the same way `04_SCOPE_TICKLIST.md` and `06_CONFORMANCE_LEDGER.md` are prior art the D14 PRDs absorbed.
Today `ADVI_FIRMBKTS` sits at L4-R ADMITTED with its L5 not started, and its decomposition will begin by re-deriving a
MAP the brief already did once in prose.

### O7 -- A committer who touches a marked surface is stopped by a gate that already exists, because the run wrote the mark the gate reads

The run's MARK is a row in `infra/logic/registry/remediations.json` naming the subject's project and the surfaces it
owns (bucket aliases and key prefixes, the file's two `surface_kinds`). `.tools/naming-gate.py` already applies DEC-6's
matrix: an EXISTING, OUT-OF-PATTERN string inside a surface a live remediation owns is REFUSED unless the diff removes
it (`.tools/naming-gate.py:706-711`). So "mark it" is not a new mechanism; it is feeding the one that is built
(IV.7). A committer who tries to add one more consumer of `opal-data-inf` after the run has marked it reads a refusal
that names the remediation project.

### O8 -- A seat re-runs the workflow on the same subject after a migration wave and reads the delta: which tensions closed, which opened, and whether the subject's ledger reached zero

Each run pins its vintage (repo HEAD, the live-graph build stamp, the registry hash) and lands in its own run
directory. Two runs on one subject are diffed on the contract, not re-read as prose: a tension row present in run N
and absent in run N+1 is CLOSED; a row absent in N and present in N+1 is NEW and is a surprise-channel row for the
project that opened it. The subject is DONE when the tension set is empty at a vintage after the last wave -- the
"ledger that can reach zero" `LGIC_CANON` promised, at subject grain.

### O9 -- Any seat runs it on any subject and gets the same contract at the same vintage

The engine is deterministic on pinned inputs: the same HEAD, the same live-graph build and the same registry hash
produce byte-identical contract files, so two seats never argue about whose run was right. This outcome exists because
this seat measured its absence today in a sibling instrument: `rcg/bin/mark.py` produced three different candidate
sets from one identical input across three runs, and the fix was one sort at the build site (`af7ee8fc55`). A
scoring instrument that varies on unchanged input is a sample, not a measurement, and a migration plan cut from a
sample is not reproducible.

# PART III -- THE QUALITATIVE BAR

Andrew: *"This does not have to be a deliverable contract. It can be qualitative because we will not know enough
about the quantitative mechanics at this point."* Each bar is disputable -- who, what, and the alternative displaced.

- **O1 passes** when a COO lane opening a migration project reads the run's contract INSTEAD of the brief's prose
  findings to know what the subject is made of, and the brief's IV sections cite the contract rather than restate it.
  It fails if the lane still opens `comp-trigger`, `EC2_MANIFEST.json` and a bucket listing by hand to fill a gap the
  contract left blank without saying so.
- **O2 passes** when a fork the estate already knows about -- the Schwab gold twin, the two MDPF gold trees, the
  `_legacy` pairs -- appears as a FORK row on the first run over its subject without anyone naming it as input. It
  fails if any of those must be told to the engine.
- **O3 passes** when every DESIRED string in the contract can be reproduced by calling the builder with the row's
  own arguments, and a reviewer who tries can. It fails the first time a desired string is found that no builder
  call produces.
- **O4 passes** when Andrew, reading the tension set for one subject, can say *"why is this above that"* and the
  answer is a row's factors, not a seat's judgment.
- **O5 passes** when the diagram is regenerated from an edited contract and changes accordingly, with no hand edit to
  the diagram file. It fails if the diagram is ever edited directly.
- **O6 passes** when `ADVI_FIRMBKTS`'s decomposition cites the run's plan as its substrate, the way the D14 PRDs cite
  `04_`/`05_`/`06_`. It fails if the decomposition re-derives the MAP.
- **O7 passes** when a deliberately planted commit adding a new hand-kept reference to a marked legacy surface is
  refused by the naming gate with the remediation project named -- in a practice worktree, with ENFORCE on (the
  gate is in its WARN window today, Part VI). It fails if the plant passes.
- **O8 passes** when two runs on one subject, at two vintages, produce a delta a reader can read as closed / opened /
  unchanged rows, without re-reading either contract.
- **O9 passes** when two runs at one pinned vintage produce byte-identical contract files, and a negative control --
  the same engine with its sort deliberately removed on a scratch branch -- produces different ones. A determinism
  test whose negative arm has never fired is a constant.

**No number here:** not a count of resource classes, not a run time, not a tension score. The ranking FACTORS are
measured values; the ORDERING is the printed rule; a weighting is a Rule 24 act for L4, if any.
