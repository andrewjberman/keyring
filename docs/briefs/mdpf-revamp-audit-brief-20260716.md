## 3. The inversion (the design's spine)

Today: feeders → mdpf gold → served JSON → DDB (registry reads the serve).
**Revamp:** monolith silver `fact_*` → **new gold `dim_*` projections** (gold = the ONE parse-down point) →
(a) `/portal` consumption artifacts + (b) the DDB rows — with the DDB as the **management/registry layer**:
cohort config, value_class, as_of/state, freshness semantics — what the page serves is generated from and
validated against the registry, not the other way around. The 14 cohort alarms then watch the thing that
actually feeds the page.

## 4. Bucketing proposal (my call, per the directive)

**`portal/{channel}/{client}/{artifact}.json` in opal-data-assets — CHANNEL-FIRST.**

```
portal/
  model-portfolios/
    global/       aggregate_aua_timeseries.json
    49financial/  aggregate_aua_timeseries.json · account_distribution.json
    inflection/   aggregate_aua_timeseries.json · account_distribution.json
  portfolios/
    global/       non_model_assets.json
  (phase-2: benchmarks/ | advisors/ | ...)
```

Why channel-first over client-first:
1. **Consumer-anchored purpose (the WP7 purpose-axis law).** A channel's artifacts version together — shape
   changes are per-PAGE, not per-firm. The page is the consumer; the folder should be anchored where the
   contract lives.
2. **"Global" is a channel-level aggregate, not a client.** Client-first forces `global/` to pretend to be
   a firm; channel-first makes it what it is — one partition among the Selected groups.
3. **The never-sum/selection law reads naturally:** within a channel, firm partitions are peers; each
   artifact labels its own basis; nothing invites cross-firm addition.
4. **Prefix-scoped access:** the page-serving role reads `portal/model-portfolios/*` — one prefix per
   surface; matches the CF router's per-page `/json/{page}/` semantics today.
5. **Client-first is the ADVI axis.** "Everything about firm X" is advisor-intelligence (0833's purpose).
   Per the WP7 amendment those purposes are deliberately kept from blurring.

Grammar note: `portal/` is a new top-level consumption root beside `{source}/{scope}/{layer}/...` — it is
purpose-anchored (consumer-side) where the ingest grammar is source-anchored; that asymmetry is the point.
New-territory rule holds: pure adds, no existing key touched.

- **YANG family = PHASE-2 (my rec).** Upload-driven vendor/market data with no monolith source today;
  different producer rhythm (PKL uploads, Step Functions, market-data DDB). Coupling it to wave 1 couples
  the revamp to a second pipeline redesign. Wave 1 = the MDPF family only; YANG keeps serving from its
  existing paths; phase-2 decides benchmarks/peers migration (+ disposition of the 2 orphan volatility legs).
- **Enumeration gap RIDES** (named residual, feed-9; headline unaffected).
- **Cutover discipline:** build alongside (new-territory rule) → parity streak vs the served mdpf artifacts
  (OPAL_CONSOLIDATION's N=3 standard) → never-widen co-signed re-point of the page/router → old path
  retires. Door 6 semantics untouched in wave 1; the mdpf trigger keeps firing until the re-point, then the
  trigger's future is a phase-2 question (the DDB-registry flow may replace the event coupling entirely).
- **Interplay noted:** INF_D_04's restore (2026-07-16, separate thread) touches the same page-family serving
  bucket but a different artifact family (platinum/firm/*); no coupling.
