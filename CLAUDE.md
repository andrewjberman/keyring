## NEVER (one miss = an incident)

- **NEVER call a client-data pipeline stale / broken / frozen / dark until you have RESOLVED THE TRADING CALENDAR — and count in TRADING DAYS, never wall-clock.** **Every AUM/holdings/trading pipeline is `T-1` unless it EXPLICITLY qualifies otherwise** (Andrew-direct 2026-07-13) — so **Friday's data IS Monday's correct answer**, and a Monday reading of "3 days / 77.0h stale" is a **HEALTHY pipeline plus a weekend**. Resolve weekends + market holidays FIRST; a wall-clock age is **not** a staleness finding, and "the number hasn't moved" is not evidence of a defect. **This is a REASONING default, not a threshold setting** — per-artifact `max_age_hours` legitimately vary; the error is jumping from *an old timestamp* to *a broken producer*. Mechanism: `lib/trading_calendar.py` is the ONE frontier definition (`expected_last_trading_day` / `trading_days_behind`); a `comp-freshness` entry without `freshness_basis: trading-day-frontier` silently falls back to flat-hours and **WILL false-alarm every Monday** — so **the instrument's own verdict is not a second opinion, it is the same error.** (Andrew-direct, *"the 100th time this scenario has happened"*: CTO, CTO~B **and** COO each independently reported the mdpf/OPAL_ASSETS table "frozen for 3 days, comp-freshness FAIL 77.0h" — two of those days were a weekend, the data was correctly at T-1, and each agent faithfully repeated the instrument.) **A FALSE OUTAGE IS NOT A SAFE ERROR: it spends credibility, and it manufactures pressure to "fix" a pipeline that is working — which is how a guard gets removed.** Record: `memory/feedback_trading_calendar_before_staleness_tminus1_default.md`.
- **NEVER** reference another firm's bucket from a pipeline tree (bd↔cot↔inf) — gate-blocked at commit + IAM Deny at runtime.
- **NEVER** move served output without never-widen sign-off (CTO+COO); a verified DELTA=0 deploy needs no hold.
- **NEVER** run bare `terraform apply` (use `safe-apply`), bare `git commit` (use `safe-commit.sh`), or `aws lambda update-function-code` (Terraform only). **GATE: `.tools/hooks/never-rules-gate.sh` (PreToolUse, `Bash|PowerShell`) — LIVE + exercised.** Audited override: `# never-override: <reason>`. Record: `docs/references/INCIDENTS_2026-07-13.md`.
- **NEVER** trigger ad-hoc gold runs to validate work — validate on the scheduled nightly's artifacts.
- **NEVER** trust a producer's self-report or rc=0 — verify against the SERVED artifact / live state.
- **NEVER** leave a confirmed deploy half-landed — a begun deploy FINISHES in-session (every prefix, leg, activation step) or rolls back + escalates loud to COO; a stranded leg is RED-ALERT material, not a follow-up. Gate: deploy-completion ledger entry in `org/critical_paths/change_management/` opened at deploy-start, closed at completion — unclosed at session end = COO alarm. - **NEVER** rebase — not `git rebase`, not `git pull --rebase` — on any shared branch (CLOUD/DEV/PROD/main/master): it rewrites multi-agent history, and a non-conflicting result is luck, not correctness. Rejected push = `git pull` (merge) then re-push. **GATE: `.tools/hooks/never-rules-gate.sh` (PreToolUse, `Bash|PowerShell`) — LIVE + exercised.** It closes all four cells (`git rebase`, `git pull --rebase`, a bare `git pull` under `pull.rebase=true`, and PowerShell). ## Deployment Rules

1. **Terraform is the only Lambda deploy mechanism.** No console, no `deploy.sh`, no direct code pushes.
2. **Commit before apply.** code → TF → source map → commit → plan → apply → 0-diff → tag → push `--follow-tags`.
3. **Dependencies go in Lambda Layers.** No `pip install -t .` into source dirs; inline vendoring needs explicit approval.
4. **Update the source map** — every Lambda has an entry in `infra/aws/lambda/ci/lambda-source-map.json` (CI drift detection).
5. **Size Lambda resources deliberately** — never leave `yang-lambda` defaults (256MB/30s) on data-processing Lambdas.
6. **Tag after deploy:** `git tag -a {pipeline}-v{X.Y.Z}` + push `--follow-tags` after every 0-diff apply.
7. **EC2 deploys go through `safe-ec2-deploy.sh`** — never run service-specific deploy scripts directly.

A DESIRED-only applied-claim, or a config-read behavioral-claim, is `INFERRED` and NON-ACTIONABLE -- the cert/dispatch owner withholds the GO (hard-withhold for SEV1/IAM/security). RAVC `grounding:` field carries `desired` + `applied` + `exercised`.
